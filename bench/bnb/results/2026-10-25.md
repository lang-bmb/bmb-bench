# BNB oracle comparison: BMB map tools against Rust file tools (2026-10-25)

The first measurement of BNB (ADR-0034 G4). On a BMB workspace and its Rust twin crate, made from the same plan, the same 27 navigation questions were solved by the scripted oracles of the two arms. No real model was run (paid, the user's machine).
Raw data: `2026-10-25.jsonl` (the code of commit `5d274c1`, `target/release/bmb`). The tables are the output of `bnb.py table`.

## Reproduction

```
cargo build --release
BMB=target/release/bmb python3 bench/bnb/bnb.py run --sizes 100 1000 10000 \
    --check-truth --cargo-check --expect all-pass --work W --out R.jsonl
python3 bench/bnb/bnb.py table R.jsonl
```

The token counts are deterministic (the same bytes when the generator, tasks, oracles and compiler output are the same). Wall-clock time is recorded and not reported.

## What was measured

- **Cost**: all bytes of tool responses of a session, tokens = ceil(bytes/4) (ADR-0021). Tokens of tool arguments (requests) were counted apart. The system prompt and the tool descriptions were not counted.
- **Accuracy**: precision and recall against the answer set; success = both are 1. The budget is the harness's (40 tool calls, `answer` included).
- **Identity of the answers**: at every size `--check-truth` compared the answers computed from the BMB map with those `analyze.py` computed from the Rust source, per task, and the whole structure (executable call and `&mut` write edges, contract edges, the io set, the duplicate groups). 0 differences at all three sizes.
- **Twin**: `cargo check` (`RUSTFLAGS=-D warnings`) passes at all three sizes.
- **Oracles**: for each arm the cheapest correct strategy found with its tools (README, "Oracles"). So the numbers below are a **lower bound** of an arm's cost.

## Interpretation

**The accuracy is the same (as expected of oracles).** Both oracles get 27/27 at all three sizes and do not reach the budget limit (max calls bmb 4, rust 17). What this measurement shows is the minimum cost of a correct answer. The comparison of accuracy (G4, "equal or better") has to come from a measurement with a real model.

**The cost of scoped tasks does not depend on the size in either arm.** At 1,000 and 10,000 they are the same to the byte (at 100 they differ because the later units do not exist and the answers are smaller). BMB is proportional to the scope of the query (principle 7). The Rust oracle is independent of the size too, because grep returns only the matching lines, and the oracle knows this crate's layout conventions (module = file, `use` of modules) and so finds callers without false matches with the regular expression `mU::f(` and a bare-name search in its own file. Asked with a bare-name grep, the same question is proportional to the size (values measured with `RustTools`, N=100/1,000/10,000):

| grep (whole crate) | Lines | Tokens |
| --- | --- | --- |
| `\bclamp_1\(` (bare name of the target of n01) | 10 / 51 / 386 | 107 / 570 / 4,479 |
| `\bmix_6\(` (bare name of the target of n03) | 13 / 151 / 1,636 | 135 / 1,629 / 18,305 |
| `^pub fn ` (every function header) | 100 / 1,000 / 10,000 | 1,222 / 12,351 / 125,957 |

The generator uses the same name stems in every unit (`mix_6`, `clamp_1` …), so name clashes may be more frequent than in a real code base. Which side a real agent is closer to is for a measurement with a real model to decide.

**On scoped tasks BMB is 3.9 times cheaper (1.7 to 12.3 times per task).** Direct callers, the impact of a contract change and functions passing a `&mut` argument are 8 to 12 times: BMB reads a few edge lines, Rust the call lines and the list of function headers of that file (to find the enclosing function). Transitive callees differ little, 1.7 to 2.0 times: `edges DEF out 64` returns the contract and `#[uses]` edges together with the call edges, so about 70% of the response rows have nothing to do with the question (n04, N=10,000: 11 `calls` rows of 38), and Rust only has to read a few function bodies. Functions that use a predicate (`requires`) are 2.2 times: Rust's grep of the `/// Requires:` lines is already precise.

**On whole-program tasks BMB's advantage shrinks, and on the duplicate questions BMB costs more.** BMB has no `duplicates` scoped to one definition and no `effects` over a set, so the oracle gets a response for the whole program. `duplicates` returns every duplicate group (12,059 tokens at 10,000), so on n27, which needs one group (132 definitions), it uses 2.8 times what Rust does (a grep of the first body line + context, 4,349 tokens). The io callers (n12, n24) read the whole `effects` (about 9,300 tokens) although the caller closure is 3 or fewer. This cost, proportional to the size, brings the ratio of the totals down to 2.1 at 10,000.

**Against the provisional G4 goal (at ten thousand definitions, a third or less of the tokens of the file-based way):** comparing the oracles' lower bounds, it is met on the scoped tasks (1/3.9) and not met on the total of the 27 tasks (1/2.1). This is not a verdict. The verdict comes from a measurement with real agents of the same model (with the input tokens the conversation accumulates over the calls). The calls are 2 to 4 per task for bmb and 4 to 17 for rust, so with a real agent, which sends the whole conversation again at every call, the accumulated input on the Rust side grows beyond this table (not counted here).

## Candidates (from the measurement, not planned work)

1. `duplicates DEF`: a scoped query that returns only the group of DEF (makes n26 and n27 independent of the size).
2. Filtering `edges` by edge kind (for example only `calls`): the transitive-callee response to about a third.
3. `effects` over a set of definitions (or the effect shown on `edges` rows): so that the io caller questions do not read the whole `effects`.

## Limits

- The oracles are lower bounds. The Rust oracle leans on layout conventions that can be learned from the first file and is correct only on the twin's fixed layout. The BMB oracle leans on the meaning of the map (the caller closure closes over `calls` edges alone). Both oracles were checked against the answers.
- The tasks are structural questions about generated code. There are no questions that need the meaning read (what does this function do) and no change tasks.
- Fixed costs of a session (the prompt, the tool descriptions: MCP `tools/list` and the 3 Rust tools) were not counted.
