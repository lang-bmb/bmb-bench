# m3 query cost scale measurement (2026-10-24)

The generator and the scale of query cost. Principle 7 ("the cost of navigation is proportional to the scope of the query") is measured at 100, 1,000 and 10,000 definitions.
Raw data: `2026-10-24.jsonl` (header row `kind:"machine"`, generation `gen`, proof `verify`, queries `query`).

## Reproduction

```
cargo build --release
python3 bench/m3/scale.py verify  --work W --out R.jsonl            # generate + cold, warm and incremental verify
python3 bench/m3/scale.py queries --work W --out R.jsonl --runs 5   # queries (MCP, warm cache)
python3 bench/m3/scale.py table R.jsonl
```

## Workspace (the generator)

`gen.py --defs N` (defaults: seed 1, 20 definitions per unit, 4 call layers, fan-out 2, a call window of 3 units, leaf contract ratio 0.5, `&mut` 0.15, array scans 0.10, `io` 0.05).
The contents of unit `mU` are fixed by (seed, U) and the parameters alone, and calls go only to the units U-3..U. So growing N only appends units at the end while the existing units stay the same byte for byte, and the definitions of unit m1 have the same callees and callers (m1..m4) whatever the size (`test_gen.py` checks this with N=100 and 200). ## Interpretation

**The response size follows principle 7.** The responses of per-definition queries (`slice`, `surface`, `edges`, `impact`, `effects`, `find` with the full path) are the same bytes on a code base 100 times larger (9 to 549 tokens). The only difference is that the `defs` key (the number of all definitions) in the summary row of `impact` and `effects` grows by 1 byte per digit. `map L0`, on the other hand, is linear at about 119 bytes per definition (2.9K → 29K → 298K tokens). At 10,000 definitions one L0 is about 300 thousand tokens and cannot be read in one go; here the reason why queries that narrow the scope are needed shows as a number. That `find inb` grows is correct behaviour: the same name exists in every unit, so the number of matches (= the scope of the query) is proportional to N.

**The response time does not follow principle 7 yet.** The CPU time of every query is nearly linear in N (about 10 times from 1,000 to 10,000: 30~50 ms → 400~510 ms). That the time is the same although the work of the query itself differs per probe is because a fixed cost dominates. Findings 1 and 2 below.

## Findings

1. **Every query reads, parses and checks the whole workspace again (proportional to N).** The MCP server too, like the CLI, reads all of `src/*.bmb` at every call, runs `frontend` and then builds the `map::Model` of the whole program (`map_request_cached` in `compiler/src/lib.rs`, `Server::files` in `compiler/src/mcp.rs`). Of the about 430 to 500 ms of CPU per query at 10,000 definitions, parsing and checking are about 330 ms (`cli check`), and the remaining 100 to 170 ms are reading the files, building the model and serialization. `effects`, whose response is 25 tokens, pays the same. Keeping the front-end result in the server's memory and processing only changed files again would remove this fixed cost (a candidate task).
2. **`surface` runs the incremental session of the whole program for the state of one definition.** Even with a warm cache it takes about 1.3 to 1.45 seconds of CPU at 10,000 definitions, about 3 times the other queries. It is the size of a warm `verify` (1.29 seconds of CPU), so it is not the solver but the key computation of 7,440 definitions and reading the cache file (`map_request_cached` calls the whole `prove` when `needs_proof`). The key of the requested definition depends only on its neighbourhood (contracts, `#[uses]`), so judging only that definition would make it proportional to the scope (a candidate task).
3. **Cold proving grows as N².** The CPU per obligation rises 3.4 → 5.8 → 32.6 ms. The cause is that the head of a query holds the declarations of every `spec fn` (the item on proof keys under "incremental build" in the compiler's README). Looking with `bmb verify --emit-smt` at the script of the same definition `m1::mix_2` (6 obligations): 19,933 bytes and 168 `declare-fun` at N=100, 90,697 bytes and 1,536 at N=1,000 (every obligation declares as many as the program has `spec fn`s). So the proof cost per definition is proportional to N and the total is N². Declaring only the `spec fn`s an obligation really uses (unfolded or mentioned by name) would make the obligation size proportional to the scope. That would also lift the limit of the incremental build that adding or removing a `spec fn` encodes every definition again (a candidate task; it changes the proof key, so ADR-0032 needs an update).
4. **Incremental verify is proportional to N too.** At 10,000 definitions an incremental verify after changing one leaf takes 1.67 seconds (1.36 seconds of CPU), most of it not proof but the front end and the computation of all keys (the same cause as findings 1 and 2).
5. **Observation (not a measured value):** during the cold verify of 10,000 definitions the RSS of the bmb process was about 680 MB (`ps`). Under load a first attempt at N=100 took 18 seconds of wall clock, on the same input as the recorded run of 1.4 seconds. Wall-clock numbers have low reliability in this environment.

## Verdict

- The generator: the generator and the gate test at N=100 (`bench/m3/test_gen.py`, the `bench m3` step of `scripts/check.sh`) are committed. All of 100, 1,000 and 10,000 are fully proved.
- The scale of query cost: response bytes and tokens are proportional to the scope of the query and independent of the whole size, as confirmed. The response time is linear in the whole size, and the causes are the whole front end redone per query (finding 1) and the whole incremental session of `surface` (finding 2). Cold proving is N² (finding 3).
